## 1. Resultado del día

Se integró lectura Siemens S7 mediante Snap7 dentro del driver existente,
conservando Modbus TCP/RTU y RS232. Se pasó de ensayos independientes a adquisición
local, monitor, catálogo SQL y persistencia simultánea con Modbus. El usuario
confirmó lectura física variando valores desde el PLC y escritura en la base real.
Se corrigió la expansión decimal de REAL, se unificó el uso del instalador y se
estableció la versión 1.3.0, sin RC ni sufijo de pruebas.

La integración de alarmas/eventos Siemens se analizó pero no se implementó.
El usuario pidió cerrar primero versión, nombre de producto y rama.

## 4. Alcance disponible

### Comunicación y adquisición

- Snap7 núcleo 1.4.3 fijado al commit oficial
  `30f37da3114024a71ba93f7fd855c680b97a406f`.
- 35 archivos del adjunto comparados byte a byte con el upstream; hashes conservados.
  Sin binarios ARM precompilados ni historial Git del adjunto en el proyecto.
- Biblioteca compartida reconstruida para la arquitectura destino; wrapper C++

- IP IPv4 numérica, puerto, rack y slot; una sesión/trabajador por PLC S7.
- DBX, DBB, DBW y DBD; tipos s7_bool, s7_byte, s7_sint, s7_word, s7_int,
  s7_dword, s7_dint y s7_real, con decodificación big-endian.
- Validación de rangos/tipos, periodos y escalas. Escalamiento multiplicativo.
- Periodos monotónicos, agrupación de tags vencidos contiguos/superpuestos,
  separación por DB y límite útil según PDU. No adelantar tags lentos.
- Timeouts y reconexión progresiva; error de DB/dirección no equivale a caída TCP.
  Un bloque rechazado puede degradarse a lecturas individuales.
- Muestras fallidas no generan ceros ni reetiquetan el último valor como nuevo.
- Monitor existente: calidad, latencias, diagnóstico, dirección, PDU y conexiones.
- Modo local sin SQL conserva recarga por SIGHUP; el arranque SQL usa las
  generaciones/recarga del catálogo habitual. No confundir ambos mecanismos.

### SQL y operación simultánea

El arranque normal carga Siemens directamente mediante JOIN de tbdispositivos y
 tbregistros por modelo. Filtra protocolo SIEMENS_S7, habilitar=1 y el concentrador
configurado. No necesita agregar columnas a qrytablacom, que no las exponía.
Usa direccion_siemens e interpretaciones s7_*, nunca registro/funcion Modbus.

Los equipos Modbus y Siemens permanecen en un mismo proceso. Siemens conserva
muestras double y usa un escritor SQL separado de sus lecturas; Modbus conserva
su escritor y comportamiento existentes. Se reutiliza la infraestructura de
sesiones SQL por hilo, monitor y gestión de trabajadores.

| Destino | Regla |
|---|---|
| tbinstantaneos | Actualizar último valor por tag/concentrador/nombredispositivo; insertar si falta |
| tbvalores | INSERT según registrable, solocambios y máximo de periodo/mínimo histórico global |
| dispositivo | ID real de tbdispositivos |
| fechatiempo | Fecha de adquisición |
| timedate | Fecha de escritura |
| registrable=0 | No impide actualizar instantáneos |
| solocambios=1 | Primera muestra y cambios respecto del histórico confirmado; REAL usa tolerancia absoluta 0.0001 |

Instantáneo e histórico debidos de una muestra S7 se guardan en la misma transacción.
Fallo previo al COMMIT: rollback y reintento. COMMIT incierto: aviso y no reintento
 automático del lote; no existe garantía de exactamente-una-vez.

Ejemplo de rastro estable en ambas tablas:

```text
Siemens_S7_1200;192.168.88.15:102;test_real;protocolo=SIEMENS_S7;rack=0;slot=1;dir=DB100.DBD8;tipo=s7_real;esc=1
```

### Precisión REAL

El usuario mostró 25.6 en TIA y 25.600000381469727 en SQL. Es la expansión de
binary32 al promocionarlo a double, no bytes inventados por la comunicación.
Se incorporó decimal corto que recupera el mismo float original, junto con un
formateador coherente para monitor y SQL. El patrón 0x41CCCCCD con escala 1 se
verificó como 25.6 en monitor, valorstr y valorfloat de ambas tablas.

No es un redondeo fijo a uno, dos o seis decimales; valores REAL vecinos siguen
siendo distintos. Los enteros, incluido DWORD máximo, mantienen su valor. DOUBLE
sigue siendo binario y el escalamiento conserva aritmética double. No se modificó
el esquema ni se reescribieron históricos anteriores.

### Diferencia entre pendientes Modbus y Siemens

Modbus sí tiene historical_pending/PendingBatch en RAM, con ventanas de hasta
mínimo/máximo/último si se habilita preservar picos. Ese mapa sobrevive a recargas
mientras siga vivo el proceso. No almacena todas las lecturas ni sobrevive a corte
eléctrico/reinicio. Conviene precisar su tratamiento de COMMIT incierto porque
un reintento puede duplicar datos.

Siemens conserva último valor y una muestra pendiente por tag, también en RAM.
No incorpora picos ni traslado de pendientes entre generaciones. Un SQL lento
puede omitir muestras intermedias. En cierre/recarga los pendientes no confirmados
se avisan; no hay promesa de recuperación total ni exactamente-una-vez.

## 10. Comandos útiles (Bash salvo bloques SQL)

### Actualizar conservando configuración y trabajo local

Detener primero la instancia correspondiente con Ctrl+C. No usar killall contra
instalaciones ajenas. Los cambios guardados en stash no se vuelven a aplicar
sobre el código actualizado automáticamente; configdb.cfg sí se restaura.

```bash
(
set -e
umask 077
cd ~/driver_modbus_pruebas
respaldo="$(mktemp -d "$HOME/respaldo-actualizacion.XXXXXX")"
cp -p configdb.cfg "$respaldo/configdb.cfg"
restaurar_config() { cp -p "$respaldo/configdb.cfg" "$HOME/driver_modbus_pruebas/configdb.cfg"; }
trap restaurar_config EXIT
git stash push -u -m "Respaldo local $(date +%Y%m%d-%H%M%S)"
git remote set-branches origin '*'
git fetch --prune origin
case "$(git branch --show-current)" in
    automonitor-driver-V1.3.0) ;;
    automonitor-modbus-driver-V1.2.0-pruebas) git branch -m automonitor-driver-V1.3.0 ;;
    *) echo "Rama distinta: revisar antes de actualizar." >&2; exit 1 ;;
esac
git branch --set-upstream-to=origin/automonitor-driver-V1.3.0
git merge --ff-only origin/automonitor-driver-V1.3.0
restaurar_config
bash install.sh --test-s7-sql
git log -1 --oneline
printf 'Configuracion respaldada: %s\n' "$respaldo"
)
```

Ese renombrado local se aplica al checkout de esta jornada, que estaba en la rama
anterior de este mismo desarrollo; no renombrar arbitrariamente otra rama si se
está trabajando en una distinta. Los cambios divergentes requieren revisión,
no reset ni force-push.

### Respaldo completo antes de cambios futuros

Ejecutar desde Bash, no dentro de MariaDB. El directorio queda privado.

```bash
(
set -e
umask 077
respaldo_dir="$(mktemp -d "$HOME/respaldo-dbdevlog-$(date +%Y%m%d-%H%M%S).XXXXXX")"
sudo mariadb-dump --single-transaction --routines --events --triggers \
    --hex-blob --databases dbdevlog > "$respaldo_dir/dbdevlog.sql"
test -s "$respaldo_dir/dbdevlog.sql"
(cd "$respaldo_dir" && sha256sum dbdevlog.sql > SHA256SUMS && sha256sum -c SHA256SUMS)
printf 'Respaldo: %s\n' "$respaldo_dir"
)
```

Checksum comprueba integridad del archivo, no una restauración. single-transaction
ofrece snapshot transaccional para tablas como InnoDB; evitar cambios de esquema
durante el dump. No incluir el respaldo ni el CFG privado en Git.
